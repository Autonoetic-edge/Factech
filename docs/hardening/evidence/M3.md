## Implementation

The isolated `packages/face-auth` profile now records authenticated self-service
consent history with scope, displayed-text version, server timestamp and monotonic
revision. Required template use and optional evaluation recording are independent.
Administrators, reviewers and operators receive no participant authority.

`privacy.py` implements a durable recording reservation and a separate encrypted
evaluation transaction. The final subject/consent lock covers storage and resource
publication, serializing withdrawal with recording. Withdrawal immediately hides
captures/receipts and schedules all linked content for purge. An application
commit failure after evaluation storage leaves an inaccessible, reclaimable
reservation. Later consent cannot retroactively record an accepted or rejected
idempotent replay. Recording outcome is reported separately from biometric outcome.

`encryption.py` replaces single-key runtime data ciphertext with per-record
AES-256-GCM envelope encryption, purpose-restricted keyrings, versioned wrapping
keys, authenticated tenant/resource/class/schema context, explicit readiness and
missing-key/tampering errors, and authenticated rewrapping. Rotation derives the
stored key-version label from the resulting envelope, including a concurrent
active-key switch. Engine/evaluation/backup providers are separate. The two-process
synthetic fixture now receives service-specific secret files that omit the other
service's data key. OS account/ACL separation remains M7, not demonstrated here.

`lifecycle.py` supplies expiry scanning, immediate access revocation, durable purge
jobs, 30-second leases, capped backoff and five total attempts. Lost acknowledgements
and repeated deletion are safe; crashes and exhausted retries leave observable
state. Ciphertext, wrapped key, scan, frames, diagnostics and accessible receipt
links are removed. Minimal proof/tombstone/job metadata remains. Original expiry
is enforced on reads and inference commit independently of purge success.

Templates require an explicit round-end deadline. Raw evaluation expiry is no
later than seven days from the server-issued challenge and may be shortened by
round expiry. Schema revisions `0003_privacy` and `0004_recovery_gate` are both M3;
head `0004_recovery_gate` does not denote implementation of milestone M4. Migration
is additive and rerunnable; old-schema applications and destructive downgrade
are refused. Legacy ciphertext requires an explicit offline conversion under its
original key; there is no runtime legacy/plaintext fallback or automatic re-encryption.

`recovery.py` provides an application-only logical backup allowlist, separate
backup encryption, a durable read quarantine shared by repository instances, and
ledger validation against an independently supplied exact digest and freshness
checkpoint. Recovery reapplies post-backup withdrawals/deletions/current consent,
removes expired/withdrawn templates, invalidates sessions/nonces, checks keys and
model fingerprints, and denies evaluation links before enabling reads. Failure
keeps the database quarantined. The old low-level `postgres.recover` does not
authorize restored reads. The approved recovery entry point is
`enable_restored_reads`; see [M3 runbook](../M3_RUNBOOK.md).
