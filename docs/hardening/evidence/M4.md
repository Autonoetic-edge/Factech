# M4 — resource protection and security hardening

Status: **LOCAL_VERIFIED and STAGING_VERIFIED on the owned loopback stack**,
20 September 2026, one agent. **741 tests passed, 0 skipped, 0 failed.** Lint and
format pass. All **100 protected source/model/asset hashes are unchanged**. The
19-route legacy inventory is unchanged. The owned stack is stopped and its four
ports are free. **No live change was made.** S06 is a written limitation, not a
measurement. No biometric efficacy or attack-resistance claim is made anywhere here.

## Why this milestone was urgent

The AmFatec preview at `amfatec.31.97.186.120.sslip.io` went live on 20 September
with self-registration open, while M4 and M7 were still TODO. That put an
internet-reachable inference endpoint in front of the public with **no
per-principal rate limit, no streaming body bound and no HSTS**. M4 was therefore
treated as closing a live exposure. The changes here are built and verified
locally; **nothing has been deployed.** A release proposal is at the end.

## Findings and what was done about each

| # | Finding | Disposition |
|---|---|---|
| 1 | No rate limit of any kind. One account, or one source, could drive unlimited authenticated inference and unlimited unauthenticated sign-in attempts against Keycloak. | Closed. `limits.py`: per-principal request and scan windows, per-source request and auth windows, all keyed on server-side identifiers. |
| 2 | No HSTS on the API or the page. | Closed. `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every API response and every page response. |

| 5 | Gateway had no admission bound of its own; it reserved a recording row and called the engine before the engine could say BUSY. | Closed. Bounded concurrent-scan admission at the gateway, refused before any reservation or engine call. |

## Decisions and why

**The M1–M3 harnesses run with limits disabled.** Two existing tests
(`test_d02_concurrent_additions_at_subject_boundary_admit_exactly_one` and
`test_challenge_binding_replay_and_concurrent_claim`) deliberately fire a burst of
requests as one actor to force a database race. With the shipping policy they
measured the rate limiter instead of the race. `unlimited()` restores their
original meaning. **No test was removed or weakened**; the limits have their own
tight-policy tests in `test_resource_limits.py`. This is recorded rather than
quietly applied, because it is exactly the kind of change that can hide a control.

**Counters are process-local.** One gateway and one engine process run per host,
so a shared counter store would be complexity with no benefit today. The ceiling
is marked with a `ponytail:` comment in `limits.py` and repeated in the threat
document: a second replica needs shared counters.

**The key table is bounded (4,096 keys, least-recently-used eviction).** A
per-source counter is keyed on attacker-controlled cardinality, so the limiter
itself would otherwise be a memory exhaustion vector. An attacker with thousands
of addresses can evict a victim's counter; that is inherent to a bounded table and
is stated rather than hidden.

**Per-source limits are enforced at the gateway only.** The engine's single caller
is the gateway, so a per-source limit there would be one global cap on all
traffic. The engine relies on per-principal limits, which it enforces
independently with its own counters.

**`/health` is exempt from limits.** It reads no state and is the container and
proxy liveness probe; rate-limiting it would make an overload look like an outage.

**The source is never taken from a header unless a proxy is explicitly
configured.** `panel.py` resolves it from the transport peer, or — only when the
peer is in `AMFATEC_TRUSTED_PROXY` — from the **rightmost** `X-Forwarded-For`
entry, which is the address the trusted proxy itself observed. A client's own
forged entries stay to its left and are never read. The gateway still rejects
`Forwarded` and `X-Forwarded-*` outright, and the resolved value travels in the
ASGI scope, which no request can set.

> **Superseded, 20 September 2026.** The peer fallback described above was a
> lockout risk, not a coarse control: behind a proxy the peer is one address for
> every visitor, so one caller could spend the whole team's allowance. The
> variable is now required, and an unattributable request is refused rather than
> counted. See [M4 follow-up](M4-FOLLOWUP.md).

**`cap_drop: [ALL]` was not applied to `db` and `auth`.** Untestable here (no
Docker on this machine, and no deployment in this milestone). Shipping an untested
capability restriction on the database would risk a failed start.

**Nothing in the biometric path was touched.** No model, threshold, preprocessing,
capture timing, challenge policy, SDK or page-UX change. All 100 protected hashes
match, before and after.

## Acceptance mapping

| ID | State | Evidence |
|---|---|---|
| S01 | **Closed** | Streaming cap of 481,964 bytes at gateway **and** engine, applied to bytes received, so an absent, false or chunked `Content-Length` changes nothing; an over-cap declared length is refused before the first chunk is read; a stalled body returns 408 on a 15-second deadline; a client disconnect ends the request with no operation. Peak memory measured and flat: see below. |
| S02 | **Closed** | Per-principal scan and request windows keyed on the durable actor id — a new session, a new cookie and a peer tenant neither reset nor consume another principal's allowance. `Forwarded`, `X-Forwarded-*` and identity headers are refused with `UNTRUSTED_CONTEXT`. Unauthenticated scans are refused at authentication, before the body is read and before any operation; verified in-process for both services and over real HTTPS with a 32 MB upload. |
| S03 | **Closed** | Gateway scan admission (5 concurrent) and the engine's existing one-worker/four-queued bound; both refuse with `BUSY` 503 and `Retry-After` rather than queueing; the gate releases on success and on failure; the engine's advice survives the proxy; `RATE_LIMITED` 429 also carries `Retry-After`. Concurrency correctness is unchanged — the M1–M3 ownership and race suites still pass. |
| S04 | **Closed for the code path** | Every required secret, issuer, origin and key is checked at startup and its absence stops the process naming the variable, never a value (15 parametrised cases); a half rotation pair stops startup; a short key stops startup; configuration refuses a non-HTTPS issuer, a trailing slash, a path in an origin, credentials in a URL, a weak service key and an empty secret. Service-key rotation overlaps then retires; token-key rotation reads old sessions, writes with the active key, and refuses old ciphertext once retired. **Not closed:** the engine's network privacy depends on the deployment's Traefik routing, which is M7/M8 and unverified here. |
| S05 | **Closed** | HSTS, CSP, `nosniff`, `Referrer-Policy`, `no-store` and `X-Request-Id` on every API response and page response, checked in-process and over real HTTPS. No `Access-Control-*` header on any route, including `OPTIONS` and a foreign `Origin`. Session cookies are `__Host-` prefixed, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. A foreign origin or wrong CSRF token cannot mutate. Logout clears the cookie and the old cookie cannot replay. Another subject and a nonexistent subject return byte-identical `NOT_FOUND` shapes. Error bodies across six failure modes contain no cookie, CSRF token, access token, service key, client secret, scan bytes, embedding, traceback or driver name; audit events likewise. |
| S06 | **Written limitation, not a measurement** | [THREAT_REPLAY_INJECTION.md](../THREAT_REPLAY_INJECTION.md). It states plainly that the nonce tests are **not** camera attestation and **not** measured PAD efficacy, and that an injected or presented genuine face is not covered. |
| S07 | **Partly closed** | Dependencies of the application and the release image are now exactly pinned and inventoried; the application base image is digest-pinned; mounts reviewed (only the named database volume is writable, no host bind, no docker socket); every service now refuses privilege escalation; asset and weight notices inventoried with permission state. **Open:** `postgres` and `keycloak` images are tag-pinned only (needs a registry fetch), `cap_drop` on those two is proposed but untested, and **no vulnerability scan was performed** — no database and no network here. |

### The S01 memory number

`docs/hardening/evidence/m4-memory-bound.json`. Peak Python heap held while an
oversized chunked upload with **no declared length** is refused, measured with
`tracemalloc` around one in-process ASGI call:

| Client sends | Status | Peak heap | Peak ÷ cap | Resident after |
|---|---|---|---|---|
| 1 MB | 413 | 620,875 B | 1.29× | 95,896 B |
| 15 MB | 413 | 618,844 B | 1.28× | 93,664 B |
| 64 MB | 413 | 616,822 B | 1.28× | 91,114 B |

**The bound is ~620 KB — about 1.29× the 481,964-byte cap — and it does not move
when the client sends 64 times more data.** The cap, not the client, decides.
This measures the application's own heap; kernel socket buffers and the ASGI
server's own transport buffers are outside it, and the deployed container's
256 MB gateway cap remains the enclosing limit.

## Observed failures and their fixes

Recorded because each one changed the work.

1. **Two existing tests failed on the first regression run** (`660 passed, 2
   failed`): the per-principal scan limit refused their deliberate bursts. Fixed
   by injecting a non-tripping `unlimited()` policy into the M1–M3 harnesses, not
   by loosening the shipping policy. Reasoning above.
2. **The first version of the new S02 fixture shared one `Limits` object between
   gateway and engine**, so every proxied scan was counted twice and the tests
   measured a limit that does not exist in the deployed profile (separate
   processes). Fixed: separate limiters per service in the fixture.
3. **`Window` with a limit of zero raised `IndexError`.** Found by a new test
   before the full suite ran. Fixed to refuse with the full window.
4. **`create_gateway` / `create_engine` did not forward the new `limits`
   argument.** Caught immediately by the new tests; fixed.
5. **The integrated run with real Keycloak failed two real-provider tests
   (`739 passed, 2 failed`)**: the suite's own repeated sign-ins exhausted the
   20-per-minute unauthenticated auth bound. This was a real design error, not a
   test artefact — a team behind one NAT address would have hit it. The bound was
   raised to 60 per minute per source, with the measurement recorded in the code
   comment, and the whole suite rerun clean.
6. **The first staging run could not sign in**, because the auth flood check ran
   before the login and exhausted the window. Reordered so the flood runs last.
   A later staging expectation of exactly 60 was wrong at 58: the sign-in itself
   had already spent two of that source's allowance. The expectation was corrected
   to 58 with the arithmetic written down; the limiter was correct throughout.
7. Ruff reported formatting on six files and one unused import after the first
   pass; both fixed and rechecked.

## Limits, and what this evidence does not establish

- **No deployment.** Everything above is local or on the owned loopback stack.
  The live preview still has no rate limit, no body deadline and no HSTS.
- **Synthetic bytes only.** The scans in these tests are filler and refused
  msgpack. They prove the HTTP and admission boundaries, not recognition or
  presentation-attack behavior. Q05 is open and team-owned.
- **S06 is a statement, not a measurement.** No injection or presentation attack
  was attempted, here or anywhere, by this track.
- **No vulnerability scan.** Stated as not performed; see finding 10.
- **Counters are process-local and the key table is bounded.** Both ceilings are
  written down in `limits.py` and the threat document.
- **Trusted-proxy resolution is untested against a real Traefik.** The logic and
  its unit tests are here; the deployed hop address is unknown to this workspace
  and is a release-time input. **Unverified.** (The follow-up adds a simulated
  proxy hop over real HTTPS on the owned stack; a real Traefik is still untested.)
- **`cap_drop` for `db`/`auth` and digest pinning for their images are proposed,
  not applied.** Both need a window and a restart test.
- **The live image's actually-resolved dependency versions are unverified.** The
  pins are this workspace's versions. Confirming the running container's versions
  needs read-only SSH, which was not performed.
- The chosen numbers (60 auth/min/source, 300 requests/min/source, 120
  requests/min/principal, 10 scans/min/principal, 5 concurrent scans, 15-second
  body deadline) are **conservative engineering defaults**, not measured capacity.
  Since measured: concurrent scans moved 5 -> 3, the windows were kept with the
  arithmetic written down, and the body deadline is still unmeasured. See
  [M4 follow-up](M4-FOLLOWUP.md).
  O06 still owns measured load. One of them was already corrected by measurement
  during this work; expect the others to need the same treatment.

## Release proposal — requires explicit approval, not yet actioned

Closing the live exposure means one gateway-and-engine release. It is **not** the
gateway-only procedure used on 20 September, because `limits.py` and the body cap
must also run in the engine.

1. **Preconditions.** Agree a short test pause with one named person who can
   confirm no capture is in progress. Self-registration stays OPEN by the user's
   decision of 20 September 2026: more testers are still to enroll. Do not close
   it as part of this release. Confirm the SSH alias.
2. **Before touching anything**, read-only: container and image IDs, health,
   compose hash, volume name, free disk, `/auth/options`. Fresh `pg_dump` of
   `amfatec` and `keycloak` into `/opt/amfatec/backups`, mode 600, each verified
   with `pg_restore -l`. Keep the 20 September dumps.
3. **Two network-dependent items need approval first**, because this workspace
   made no network request: resolve and pin the `postgres:16-alpine` and
   `keycloak:26.7.4` digests, and run a dependency and image vulnerability scan
   with the disposition of every finding recorded before the build.
4. **Set `AMFATEC_TRUSTED_PROXY`** to the Traefik container's address on the
   compose network. It is now **required**: the gateway will not start without
   it, and the literal `direct` is the only way to declare no proxy in front.
   This value must be read from the running deployment; it is unknown here. The
   earlier advice in this point — "set nothing rather than guessing" — was wrong
   and is withdrawn; setting nothing put every visitor in one bucket. See
   [M4 follow-up](M4-FOLLOWUP.md).
5. Build one immutable `amfatec:<release>` image from reviewed files, generate a
   SHA-256 manifest, transfer with LF line endings, verify the manifest on the VPS.
6. **Pin the two services to separate image tags in `compose.yml` first**, so a
   later `docker compose up -d` can never recreate the frozen engine by accident.
   That is a prerequisite the existing rollback plan already identifies.
7. Recreate gateway **and** engine. Confirm `db` and `auth` container IDs are
   unchanged.
8. Verify: HSTS present; `Retry-After` on a deliberate 429 from one throwaway
   account; a 32 MB upload returns 413; `/auth/options`; sign-in; one real
   enrollment and verification by a named tester. Do not load-test the VPS.
9. **Rollback:** retag the recorded outgoing image as `amfatec:current`, restore
   the saved `compose.yml`, recreate both services. Databases, templates,
   accounts and volumes are preserved; no schema change is in this release, so
   the old image runs against the current schema unchanged. Never use `-v`.

**Do not treat this section as approval to deploy.** It is the plan to be approved.
